# Local Suunto running summaries

Suunto is optional and independent from Oura. Recovery, sleep, readiness and guidance physiology remain Oura-only. The Suunto worker imports an allowlist of running workout summaries from the v3 workouts endpoint; it never requests FIT, GPS, routes, names or heart-rate traces. Running sport IDs are 1, 22, 53, 59, 60, 103 and 115.

Run `python -m app.suunto_worker` as a separate service sharing the application database. Only that service receives a read/write `SUUNTO_SECRETS_DIR` directory (default `/run/suunto-secrets`) containing `configuration.json` (`client_id`, `client_secret`, `subscription_key`) and `tokens.json` (`access_token`, `refresh_token`). OAuth setup uses the existing local authorization helper. Refresh requests use HTTP Basic client authentication, and preserve the existing refresh token when the provider omits a replacement (per [OAuth 2.0 §6](https://www.rfc-editor.org/rfc/rfc6749#section-6); [Suunto authentication](https://apizone.suunto.com/faq)). A PostgreSQL session advisory lock admits one Suunto worker; refreshed tokens are saved atomically with mode 0600 before retrying. Never mount this directory into the Oura worker, API, frontend or MCP. Set `SUUNTO_ENABLED=true` consistently for API and Suunto worker after authorization; no credentials are needed to read status. With it absent/false, status is unconfigured, manual sync returns 409, and health/Oura continue normally.

The worker syncs once per day or on a manual request; `SUUNTO_SYNC_INTERVAL_SECONDS` defaults to 86400 and cannot lower that interval. `SUUNTO_SYNC_LOOKBACK_DAYS` defaults to 90 (1–365). The rolling seven-day persisted request budget is 160, below the provider's 200/week cap; ten requests per minute and ten per job include refreshes, retries and failures. Requests are reserved before transport, so a crash can consume budget conservatively. Jobs and 429 Retry-After backoff survive restart. Missing/invalid Retry-After pauses collection for a day. A manual retry during backoff fails without a provider call. Collection uses fixed HTTPS endpoints, redirects disabled, bounded offset pagination (eight pages of fifty), repeated-page detection, and never follows metadata URLs. A page-limit failure may leave already imported summaries; the job is failed and coverage unconfirmed.

`GET /api/suunto/status` exposes configuration, latest job, last successful collection, rolling budget and backoff. `POST /api/suunto/sync` queues/coalesces an independent owner-scoped job; `GET /api/suunto/sync/{id}` reads it. Browser write origin checks match Oura. Sync jobs never write plans or mark sessions complete.

Normalized records store only provider ID, running activity ID, provider-offset day (explicit UTC fallback if absent), UTC start/stop, distance, active duration, elapsed duration and their interpretation. Epoch seconds and milliseconds are validated. Stop time is never invented from active duration.

The shared running context powers dashboard, MCP and planner observation. A one-to-one cross-provider overlap with both start and end within two minutes keeps Suunto distance and active duration, records both provenance sources and excludes the Oura copy. Missing Suunto distance remains missing. Other overlaps are flagged ambiguous, retained for review, and excluded from distance totals and longest-run estimates; separate same-day runs remain separate. Oura-only runs are explicit fallbacks. Elapsed pace uses elapsed time, never active time presented as elapsed. Incomplete weeks, missing workouts and ambiguous totals do not establish rest, race fitness, completion, or permission to increase plan mileage or pace.

Verification uses only synthetic data in `backend/tests/test_suunto.py` and existing running/planning/recovery/API/MCP tests. No real provider calls or secrets are needed.

`GET /api/running/context` defaults to the last 28 complete provider days for planner observation. The dashboard requests `?include_today=true` to include the current partial provider day; the response flags `includes_partial_today`. `visible_records` includes ambiguous records and sessions without a confirmed past stop; `recorded_runs`, distance totals and longest-run estimates exclude them. Only projected summary fields are exposed from stored Suunto records.
